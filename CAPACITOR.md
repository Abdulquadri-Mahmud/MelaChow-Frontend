# Customer Capacitor app

The customer frontend now has bundled Capacitor 8 Android and iOS targets:
`com.melachow.customer`, displayed as **MelaChow**. Website builds still use
`npm run build` and the original Next.js configuration. Vendor/rider apps
are not generated by these commands.

## Build on Windows

1. Android Studio and Android SDK Platform 36 are installed on the audited Windows PC. Use the installed Microsoft JDK 21 for command-line builds.
2. In SDK Manager install Android SDK Platform 36, Platform Tools, and the
   Build Tools requested by Gradle.
3. Use Node.js 22 or newer. If PowerShell blocks npm.ps1, use npm.cmd and npx.cmd.
4. Copy `.env.mobile.example` to `.env.mobile.local`. Confirm
   `NEXT_PUBLIC_MOBILE_API_URL` is your intended backend's HTTPS origin,
   without `/api`. The example matches the existing website's fallback;
   it is not a verified production environment assignment.
   Add the Google Maps public key used by address autocomplete if needed.
   Never put backend secrets in NEXT_PUBLIC variables.
5. For command-line Android builds, point JAVA_HOME at Android Studio's JDK:

```powershell
$env:JAVA_HOME = "C:\Program Files\Android\Android Studio\jbr"
npm.cmd run mobile:doctor
npm.cmd run mobile:apk
```

`mobile:apk` checks prerequisites, builds the frontend, syncs Android, and runs
Gradle's debug build. Result:

```
android/app/build/outputs/apk/debug/app-debug.apk
```

Install that APK directly on a phone, or enable USB debugging, connect the phone,
then open Android Studio with `npm.cmd run mobile:open` and use Run.
No emulator or Play Console account is needed for local testing.

Individual commands:

| Command | Purpose |
| --- | --- |
| npm.cmd run mobile:doctor | Check Node, Android SDK 36, and Java |
| npm.cmd run mobile:build | Generate the static customer web bundle |
| npm.cmd run mobile:sync | Rebuild and copy it into Android |
| npm.cmd run mobile:open | Open the native project in Android Studio |
| npm.cmd run mobile:preview | Serve the latest export at http://127.0.0.1:4173 |
| npm.cmd run test:mobile | Pure routing and API URL tests |
| npm.cmd run test:mobile:browser | Edge smoke tests with mocked external services |

The browser tests currently expect the example API origin. If building against
another origin, set `MOBILE_TEST_API_ORIGIN` to that same origin when testing.
Set PLAYWRIGHT_CHANNEL=chrome if Edge is unavailable. Tests do not log in to
production, create orders, charge cards, or upload files.

On the audited PC: Node 24, JDK 21, Android Studio, Android SDK Platform 36, and build tools are available. The debug APK builds successfully. A physical phone remains preferable to an emulator on this 8 GB, fourth-generation Core i5 laptop.

## How the mobile build works

`scripts/build-mobile.mjs` creates an ignored `.mobile-build` directory from the
current frontend source. It applies explicit mobile overrides there and uses
Next's static export. It never removes or relocates the website's source routes.
Edit shared product UI in `src`; edit native adapters in `mobile`. Never edit
`.mobile-build` or copied Android web assets.

The build rejects unexpected dynamic routes and mismatched overrides rather than
silently packaging a broken app. Add any new dynamic route to
`mobile/routes.mjs` and review the build adapter.

| Website route | Packaged mobile route |
| --- | --- |
| /food-details/:foodId | /food-details/?foodId=... |
| /combo-details/:comboId | /combo-details/?comboId=... |
| /restaurants/:vendorId | /restaurants/?vendorId=... |
| /track-orders/:orderId | /track-orders/?orderId=... |
| /get-help/tickets/:ticketId | /get-help/tickets/?ticketId=... |

Link/router adapters translate customer links and preserve pathname checks used
by auth guards and navigation. Detail components load live data on the device;
no current database IDs or private orders are baked into the APK.

## Audit findings and handling

- **Android local routing:** Capacitor normally falls back to the root index.html
  for extensionless paths. MainActivity maps local main-document requests to the
  corresponding exported directory/index.html and delegates back to Capacitor
  for bridge injection. JavaScript assets and Next RSC requests are untouched.
  This native adapter has been compiled successfully; behavior still needs real-device testing.

- **Next.js server dependence:** API rewrites, proxy redirects, runtime detail
  metadata, sitemap fetching, and image optimization need a Next server.
  The website retains these features. The mobile export omits the server-only
  pieces, exports client detail pages, and uses unoptimized remote images.
- **API and authentication:** relative /api and /v1 requests would hit the local
  app server. Mobile fetch and axios adapters resolve them to the explicit API
  origin. CapacitorHttp routes fetch/XHR through native networking. Customer
  bearer credentials are added only to that API origin; native refresh cookies
  still need real-device verification. Existing website token persistence uses
  localStorage; encrypted native storage remains a production hardening task.
  Android backup is disabled for this app.
- **API access policy:** the inspected backend permits HTTP requests without an
  Origin header, which native HTTP commonly uses. If requests include the native
  origin, allow exactly https://localhost for Android (capacitor://localhost for
  a future iOS target) in HTTP/Socket.IO origin configuration. Do not use a
  wildcard with credentials. The deployed backend configuration was not changed.
  Socket.IO continues to use its direct backend URL and bearer authentication.
- **Payments:** backend responses already include a reference, but existing web
  flows navigate away to Paystack. Mobile opens the HTTPS payment URL through
  Capacitor Browser and persists the pending reference. On returning, the user
  can tap Check payment to invoke the existing server verification page. Neither
  returning to the app nor receiving a deep link marks an order as paid.
  Existing web callbacks remain usable; automatic verified HTTPS App Links
  require domain association and release signing configuration.
- **Deep links and Android navigation:** Android Back uses history, then returns
  to Home, then minimizes the app. The manifest supports
  `melachow://app/verify-payment?reference=...` and other customer paths.
  Public website links and this app scheme are accepted; foreign domains are
  not accepted as app deep links. Custom schemes are not verified App Links.
- **Location:** Android coarse/fine location permissions and Capacitor Geolocation
  support the existing delivery-pin workflow. GPS is optional for installation.
  Location denial, approximate location, and accuracy need phone testing.
  Google Maps key restrictions must allow the app's origin for web autocomplete.
- **PWA and notifications:** mobile overrides suppress service-worker registration,
  installation prompts, and browser web-push controls. Existing foreground
  Socket.IO/REST notifications remain. Background push is not implemented:
  it requires Firebase configuration, native device-token registration, and
  backend FCM delivery; existing web-push subscriptions cannot be reused.
- **Screen/keyboard:** the Android activity draws edge-to-edge and applies
  system-bar/cutout insets once to the app content. Capacitor's duplicate
  SystemBars inset handler is disabled; the status and gesture bar surfaces are
  white with dark icons.
- **Branding:** Android's native launch screen uses `public/logo.png`. The
  WebView loading surface is plain white so the logo does not appear a second
  time before the customer in-app splash, which uses the vendor splash artwork
  and animated loading dots. App signing and store graphics are still release
  preparation.
- **Dependency audit:** The Capacitor reinstall reported 32 dependency advisories
  (1 low, 8 moderate, 23 high). These are not all newly introduced runtime issues.
  Review npm audit and dependency upgrades separately; no force upgrades were
  applied.

## Validation and remaining device checks

Validated here: static export, route/API unit tests, mocked Edge smoke tests,
targeted lint, and Capacitor Android sync. Browser tests cannot validate Java,
Android WebView behavior, native cookie persistence, or Android plugin permissions.

Before distributing an APK, test on a phone: signup/signin, session restoration
after force-stop, refresh/logout, restaurant and food links, cart and checkout,
payment success/cancellation/return, wallet funding, live order tracking,
delivery-pin permissions, image uploads, offline errors, keyboard, Android Back,
and cold-start links. Use a staging backend and payment test mode.

The Android project targets API 36 and supports Android API 24+.
The iOS native project is generated and synchronized. Building, signing, and device validation require macOS with Xcode. No signed release, store upload, or production deployment was made.

Because the APK contains a packaged copy of the frontend code. Once installed, that code remains fixed until a newer APK replaces it.

A rebuild is required when changing:

- Pages, styling, components, or JavaScript bundled inside the app
- Capacitor configuration
- Android permissions
- App icons or splash screens
- Native plugins
- Package name or Android configuration

A rebuild is usually unnecessary when changing:

- Backend API logic
- PostgreSQL data
- Backend environment variables
- Server side authentication or CORS
- Content fetched dynamically from the API

For faster development, we can configure the vendor app for **live reload**:

1. Run the frontend development server on your PC.
2. Point Capacitor to your PC’s local network address.
3. Open the already installed app.
4. Frontend changes appear automatically without rebuilding the APK.

Your phone and PC must be connected to the same Wi-Fi network. We should use live reload only for development. The final Play Store APK/AAB should always contain a production build and use the staging or production HTTPS API.
